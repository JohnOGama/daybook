# Vault Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Vault space tool that stores cards, IDs, logins, keys and free-form items, encrypted in the browser, with a recovery key and encrypted backup export and import.

**Architecture:** Pure crypto, backup and content modules live in `apps/web/src/features/vault/src` and use Web Crypto. A session provider above the routes holds the non-extractable vault key in memory. The Nest `vault` feature stores only base64 ciphertext, wrapped keys and salts, scoped by `userId`.

**Tech Stack:** Next.js, React Query, shadcn/ui, Web Crypto (no new dependency), NestJS, Drizzle, Postgres, Vitest, PGlite.

**Spec:** `docs/superpowers/specs/2026-11-10-vault-design.md`. Mockup: `docs/superpowers/specs/vault.html`.

## Global Constraints

- The owner commits their own work. Do not run `git commit`. Finish with a ready-to-paste commit message.
- Follow `CLAUDE.md`: components end `Component`, hooks `useX`, utilities kebab-case, `page.tsx` only composes, relative API imports include `.ts`, every constructor dependency has `@Inject(Token)`.
- Every API query is scoped to `userId` and soft-deleted rows are filtered with `isNull(deletedAt)`.
- The passcode, the vault key, the recovery key and decrypted content never reach the server, React Query's cache, local or session storage, the URL, toasts or logs. Toasts stay generic: "Item saved", "Copied. Clipboard clears in 30 seconds."
- Minimum passcode length 12. PBKDF2-SHA-256, 16-byte salt, at least 600,000 iterations. AES-GCM with 256-bit keys and 12-byte IVs. Item ciphertext at most 64 KB. Import at most 2,000 items and 8 MB.
- Theme tokens only. Colour is reserved for `destructive`, `signal` and `status-*`. Loading states use Skullet.
- Any test that calls `crypto.subtle` directly starts with `// @vitest-environment node`, because jsdom's typed arrays can fail Web Crypto's checks.

## Review Focus

- A recovery key typed in lowercase, with spaces or without dashes should still work. Task 1.
- A passcode typed with different Unicode composition (`é` as one or two code points) should still unlock. Task 1.
- A file that isn't JSON, isn't a backup, or is over the limits should show an error and import nothing. Task 2.
- Two tabs creating a vault at once: the second gets a clear message and doesn't overwrite the first. Tasks 4 and 8.
- The idle lock firing while the Add item form is open should clear the form and values without crashing. Task 9.

- [ ] **Step 3: Implement `vault-crypto.ts`**

Passcodes pass through `.normalize('NFKC')`. `wrappedKey` and `recoveryWrappedKey` are base64 of a 12-byte IV followed by the 48-byte AES-GCM wrap, 60 bytes in total. The recovery key is 20 random bytes in RFC 4648 base-32; parsing strips non-alphanumerics, uppercases, and requires 32 alphabet characters. Its wrapping key comes from HKDF-SHA-256 with `recoverySalt` and info `daybook-vault-recovery-v1`. Item AAD is `new TextEncoder().encode(id)`. `createVault` and every re-wrap unwrap an extractable copy only inside the function; returned keys are non-extractable. Any AES-GCM `OperationError` becomes `WrongSecretError`.
