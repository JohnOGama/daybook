# Fitness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Fitness space tool: a food log against calorie and macro targets, meal plans and workout templates applied to a day, a weight log with a forecast, a muscle diagram, and an AI read.

**Architecture:** Follows the Budget tool. A `fitness` space tool, a NestJS feature (`apps/api/src/features/fitness`) that stores rows and checks ownership and the space lock, and a web feature (`apps/web/src/features/fitness`) that computes targets, totals and the forecast in the browser with small tested functions. Built-in foods (USDA SR Legacy) and exercises are shared read-only rows loaded by import scripts. Meal plans, workout templates and workouts store their items as one JSON document each.

**Tech Stack:** Next.js (read `apps/web/node_modules/next/dist/docs/` first), NestJS through `tsx`, Drizzle on Postgres (PGlite in tests), React Query, shadcn/ui, Skullet, zod, `@google/genai` through the existing `BudgetAiService`.

**Spec:** `docs/superpowers/specs/2026-11-13-fitness-design.md`. Read it with this plan; `CLAUDE.md` gives the project rules.

## Global Constraints

- Every service query is scoped to `userId`; every route that returns a space's contents calls `SpaceLockService.assertUnlocked` first.
- Every constructor dependency in the API needs an explicit `@Inject(Token)`. API relative imports end in `.ts`; web imports use `@/`.
- "Today" is the browser's local date from `useToday`, sent on requests. Never the server clock.
- Whole numbers in the database, no floats: food weight and macros in milligrams (`...Mg`), energy in whole kcal, body weight in grams (`weightG`), height in millimetres (`heightMm`), a serving count in thousandths (`quantityMilli`).
- A logged food stores its own name, kcal and macros. Editing or deleting a food, plan or template never changes a day already filled in.
- Nothing is logged automatically. Planned food (`eaten: false`) and planned sets (`done: false`) never count towards totals.
- Metric only. Seventeen muscle ids, exactly: `neck, traps, shoulders, chest, biceps, triceps, forearms, abs, lats, middleBack, lowerBack, glutes, abductors, adductors, quads, hamstrings, calves`.
- Dark, monochrome UI with theme tokens; colour only through `signal` and `destructive`. Skullet for every loading state. Components end in `Component`, hooks start with `use`, other files are kebab-case, `page.tsx` only renders the page component.
- Mutations are optimistic with client-generated ids (`crypto.randomUUID()`), snapshot and restore on error, toast on failure, no refetch on success.
- The AI is sent summary figures only, never food names, notes or the space title, and every reply is checked against a zod schema.
- After schema edits run `pnpm --filter api db:generate` and rename the migration to `00NN_fitness_<what>.sql` (update `drizzle/meta/_journal.json` to match). Do not run `db:migrate`; the owner applies migrations.
- After each task run `graphify update .`. Commit only if the owner has asked for commits; otherwise leave a commit message per task.

## Review Focus

1. A profile with no weigh-in, height or birth date yet: targets, BMI and forecast show "add your weight/height" prompts, never `NaN` or `Infinity`. (Task 1, Task 5)
2. Amounts typed as `1,5`, `0`, negative, or empty: a comma is read as a decimal point; zero, negative and non-numbers are refused in the form and by the API schema. (Task 3)
3. A custom food deleted after it was logged, or a built-in food's serving removed: past log rows still show their name and numbers. (Task 3)
4. Food search text containing `%`, `_` or a quote: treated as plain characters, no error, no match-everything. (Task 2)
5. Averages over days with nothing logged: those days are left out, and a week with no logged days shows a dash, not zero. (Task 5)
