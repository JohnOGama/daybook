# Sharing rules

## Sharing rules

- `space_shares` rows are keyed by lowercased email, so an invite works before the person signs up. A share on a folder or space covers everything under it, the best role wins, and a deleted ancestor hides the share. A Vault is shared only once it has a sharing passcode (below).
- Every space-content route calls `SpaceAccessService` (`resolve`, `resolveRow`, `resolveRows`) first and passes the returned `ownerId` to the unchanged services. No access is 404; view-only on a write is 403; AI routes need edit. Trash, the personal vault routes (passcode, recovery key, erase) and the owner-only space routes (rename, delete, move, duplicate) answer 404 to recipients. `resolveRow` does not check `deletedAt`, so keep the live-row check.
- `SpaceLockService` looks up by space id only, so callers resolve access first. The unlock cookie is signed with the viewer's own user id, recipients need the password, and only the owner can reset or remove it.
- Whole-document saves (notebook page content, meal plans, workout templates, workouts) carry a `version` integer. A stale one answers 409 "Changed by someone else", and editors send the version they opened with; the web offers Reload.
- Share routes are on `SpacesController` (`/spaces/:id/shares`, plus `/shares/me` to leave). The web `Space` has `access`, `shared`, `ownerId` and `ownerName`; read access through `useSpaceAccess()` (`access`, `canEdit`, `isOwner`). Every tool hides edit controls and automatic writes (budget schedule catch-up, diagram table placement) for viewers.
- Sidebar groups (`space_groups`, `/space-groups`) are the owner's only: each top-level folder or space carries `groupId`, a space in a folder follows its folder, and spaces shared with you have none (they stay under Shared with me). The first read makes a "Spaces" group if there is none, and new top-level items without a group go into the first one. Deleting a group soft-deletes it and its top-level items (so Trash, shares and pipeline keys behave as for a deleted folder); restoring any of them brings the group back. Your last group can't be deleted. Settings → Spaces reorders groups by dragging a row's grip (`PUT /space-groups/order` with every group id once, optimistic). `PUT /spaces/:id/group` moves a folder or space to another group (a space in a folder leaves it), last there or at the spot an optional `order` gives; the sidebar sends that when a row is dropped on another group, or a space is dragged out of its folder. Dragging does every Move to move (`dropAction` in `sidebar-drop.ts`): a space dropped on the middle of one of your folders' headers, or on a space inside another of your folders, goes into that folder (last, through `PUT /spaces/:id/parent`). Every row you own drags from anywhere on the row (after 4 px, so clicks still work); its grip handle only shows on keyboard focus and touch screens. While dragging, the row fades in place and a copy (`DragPreview`, a `DragOverlay`) follows the pointer, saying "Into <folder>" or "To <group>" when the drop would change either; a line shows where it lands in a group, and the folder it would go into is outlined. Shared rows don't drag.
- **Shared Vaults.** Every Vault is encrypted in the browser with the owner's one vault key, which covers all their Vaults, so a Vault to be shared first gets its own key. The owner sets a **sharing passcode** (Vault options → Sharing passcode, `SharingPasscodeDialogComponent`): the browser makes a new AES key, wraps it with that passcode (PBKDF2, like the vault passcode) and seals it with the owner's vault key (`ownerWrappedKey`), re-encrypts every item in the space, trashed ones too (`GET /vault/items?includeDeleted=true`), and sends key and items together in one `PUT /vault/spaces/:spaceId/key`, which answers 409 unless the items are exactly the space's. Later changes only re-wrap the key. One `vault_space_keys` row per space holds the wraps; the server never sees the passcode or any key.
  - Until that row exists, sharing the Vault answers 400 ("Set a sharing passcode for this vault first") and `SpaceAccessService` hides it from everyone else, also through a shared folder.
  - People it is shared with skip their own vault entirely: they type the sharing passcode (`VaultSharedLockedComponent`), which the owner tells them outside Daybook. The owner opens it as before with their own passcode, and `useItemKey` opens the space key from `ownerWrappedKey`. `GET /vault/spaces/:spaceId/key` sends `ownerWrappedKey` to the owner only. Opened space keys live in the vault session (`spaceKeys`) and lock with it.
  - Editors add, edit and delete items, written under the owner (deleted ones go to the owner's Trash); viewers only read and copy. Backups, passcodes, the recovery key and erasing stay the owner's. An exported backup re-seals a shared Vault's items with the owner's vault key, so it opens with the owner's passcode as before. Erasing the owner's vault drops their sharing keys, which stops those Vaults being shared.
  - Removing someone's share stops the server sending them anything, but they may have kept what they saw; change the passcode and the secrets themselves if that matters. There is no live presence in a Vault.
