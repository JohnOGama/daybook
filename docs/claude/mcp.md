# MCP rules

## MCP rules

- **What it is.** AI apps (ChatGPT, Claude, Gemini CLI) connect to `POST /api/mcp` (`features/mcp`) and log food, workouts and weigh-ins in the person's Fitness spaces. The person adds `<site>/api/mcp` as a custom connector in the app.
- **Requirements:**
  - ChatGPT and claude.ai call from their own servers, so they need the public HTTPS site, or a `cloudflared tunnel --url http://localhost:3000` while developing.
  - `localhost` works only for local clients (MCP Inspector, Claude Code, Gemini CLI).
- **Sign-in is Daybook's own OAuth.** Better Auth runs the `jwt` plugin and `@better-auth/oauth-provider` (`create-auth.ts`). Apps register themselves (dynamic registration, public clients allowed), PKCE is required, and the scopes are `openid`, `profile`, `offline_access` and `fitness`.
  - Access tokens are JWTs for the audience `<BETTER_AUTH_URL>/api/mcp` (`mcpUrlFor`) and last 1 hour. Refresh tokens last 30 days.
  - An app that leaves out `resource` gets the MCP URL anyway. A before-hook fills it in on `/oauth2/authorize` and `/oauth2/token`, because otherwise the provider issues an opaque token `/api/mcp` can't check.
  - The plugin tables live in `auth-schema.ts`, generated by the drizzle adapter's generator at 1.7.18 (migration `0027_oauth_provider`).
- **The flow in the web:**
  - The provider sends a person who isn't signed in to `/sign-in` with a signed query (`sig`).
  - `oauthProviderClient()` in `auth-client.ts` attaches that query to the sign-in, and `SignInPageComponent` follows the returned `url` back to the app.
  - `useRedirectIfSignedIn` doesn't send people to `/list` while `sig` is in the URL.
  - Consent is `/oauth/consent` (`OAuthConsentPageComponent`, a signed-in `AuthCardComponent`), shown once per app and scope set.
  - Anyone can register an app under any name, so the consent page shows the host of the signed `redirect_uri` ("After you allow it, you'll go back to claude.ai.").
  - `withWaitingApp` (`oauth-request.ts`) carries the signed query through `/verify`, `/sign-up` and `/forgot-password`, so verifying an email or resetting a password mid-connect still ends back at the app.
- **Discovery.**
  - `mountWellKnown` (`main.ts`) serves the authorization-server metadata (`/.well-known/oauth-authorization-server`, also with the issuer path appended), `openid-configuration` and the protected-resource metadata (`/.well-known/oauth-protected-resource`, also as `/api/mcp`).
  - Next rewrites `/.well-known/*` to the API.
  - The production nginx config sends every path (`location /`) to the same upstream, so it needs no change.
- **The endpoint** (`McpEndpoint`, mounted in `main.ts` before the JSON parser with its own 1 MB limit):
  - It is the official MCP SDK's Streamable HTTP transport, stateless and answering in JSON. GET and DELETE answer 405.
  - A missing or bad token answers 401 with `WWW-Authenticate: Bearer resource_metadata="<site>/.well-known/oauth-protected-resource/api/mcp"`.
  - `verifyMcpToken` checks the JWT against Daybook's JWKS (issuer, audience, expiry), the `fitness` scope, and that the app's consent still exists. That last check is what makes Disconnect take effect before the token expires.
- **The tools** (`FitnessMcpTools`, registered in `mcp-server.ts`):
  - The tools are `list_fitness_spaces`, `search_foods`, `log_food`, `search_exercises`, `log_workout`, `get_day`, `remove_food_log`, `remove_workout` and `log_weight`.
  - **Rules every tool follows:**
    - They act as the approving person, through `SpaceAccessService.resolve(…, 'edit')`, Fitness spaces only, writing under the space owner like the app's routes.
    - Locked spaces are out of reach (there is no unlock cookie): they are left out of the list and refused by id.
    - `spaceId` may be left out only when the person has exactly one editable Fitness space; otherwise the tool answers with the choice.
    - Every `day` is required as the user's local `YYYY-MM-DD`; nothing defaults to today.
  - **Logging food:**
    - Units at the boundary are grams, servings, kg, seconds and meters. A food by id is worked out like the web's `itemFor` (`food-amounts.ts`).
    - A one-off food is a log with `foodId: null` and the assistant's own estimate, never a stored food.
    - Built items are checked against `foodItemFields` and `workoutSchema`, so the app's limits hold.
    - A by-name exercise is `weight` when a set has kg, `time` when one has seconds or meters, else `reps`; a found exercise keeps its own kind.
    - Food logs are eaten and workout sets are done. `get_day` totals count eaten rows only.
  - **Errors:**
    - Problems come back as tool errors in plain sentences (`ToolError`, or a Nest 4xx's message).
    - Anything else is logged and answered "Something went wrong in Daybook. Try again."
- **Connected apps.**
  - `GET /api/connected-apps` lists the person's consents with the app's name.
  - `DELETE /api/connected-apps/:id` deletes that consent and the app's access and refresh tokens in one transaction (the plugin's own delete-consent leaves tokens behind).
  - The web is Settings → Connected apps (`features/connected-apps`, `['connected-apps']`). Disconnect is optimistic, with no Undo.
- **Open edge.** `/api/auth/oauth2/register` accepts anyone, so rate limit it with sign-in (README, "Before deploying").
