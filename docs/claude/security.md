# Security rules

## Security rules

- A Security space (inspired by the [xalgorix](https://github.com/xalgorix/xalgorix) findings model) tracks security findings. It does **not** scan, exploit or call any AI: findings are entered by hand or imported. Each finding is one `security_findings` row with a title, an optional `target` (the affected URL, host or component), a `severity`, a `status` and an optional `cvss`.
- `severity` is `critical | high | medium | low | info`; `status` is `open | triaged | fixed | accepted`. `cvss` is the base score in **tenths** (an integer 0–100, i.e. score×10), so no float is stored; null when unset. The web parses and formats it with `cvssToTenths`/`formatCvss` in `security-math.ts`. `owasp` is the OWASP Top 10 (2021) category code `A01`–`A10` (nullable), labelled by `OWASP_LABELS`; it is settable on manual findings and set automatically by the scan.
- The risk overview, the open counts and the table sort are computed in the browser (`features/security/src/security-math.ts`); the API only stores and checks ownership. A finding counts as open while it is `open` or `triaged` (`isOpen`); `fixed` and `accepted` drop out of the overview but stay in the table, dimmed.
- Findings are **hard-deleted** (the space itself still goes to Trash). Deleting a finding is optimistic in the web, with a rollback toast on failure, like the rest of Daybook; there is no Undo.
- Routes (`/security`; reads also need the unlock cookie), all owner-scoped through `SpaceAccessService` and refusing a non-Security space with 404:
  - `GET /:spaceId` (view): the space's findings, newest first.
  - `POST /:spaceId/findings` (edit, at most 500 per space): create one.
  - `PATCH /findings/:id` (edit): change only the fields sent (`updateFindingSchema` is all-optional); `target`, `cvss` and `description` take `null` to clear.
  - `DELETE /findings/:id` (edit): hard-delete.
- **Passive scan.** `POST /:spaceId/scan` (edit) takes `{ url, authorized: true }`; `authorized` is a `z.literal(true)`, so a scan is refused (400) until the person confirms they own or may test the target, before any request is made. It is rate-limited to once every 10 s per space (429, in memory). `security-scan.ts` fetches the URL with **ordinary GET requests only** — no cookies, no attack payloads, at most 3 redirects, 10 s, 256 KB — and every resolved address must pass `isPublicAddress` in the socket `lookup` (shared with the jobs posting fetcher and the uptime checker), so it can never reach a private host. It reads the response headers, cookies, TLS and the page's HTML, runs OWASP-aligned deterministic checks, and stores each result as an open finding tagged with its OWASP category. The check groups (`security-scan.ts`) are: **transport & TLS** (plain HTTP, missing/weak HSTS, mixed content — A02), **security headers** (CSP presence and `unsafe-inline`/`unsafe-eval` strength, X-Frame-Options/frame-ancestors, nosniff, Referrer-Policy, Permissions-Policy, COOP, CORP — A05), **CORS** (`Access-Control-Allow-Origin: *`, worse with credentials — A05/A01), **cookies** (Secure/HttpOnly/SameSite and `__Host-`/`__Secure-` prefix rules — A07/A05), **page content** (forms posting to `http://`, passwords collected without TLS, read from the fetched HTML — A02/A07), and **information disclosure** (Server/X-Powered-By/ASP.NET version banners and the `generator` meta tag — A06). There is **no active exploitation, fuzzing, probing of other endpoints or payloads**; every check reads only the one fetched response. This is surface analysis, like securityheaders.com or Mozilla Observatory.
- **Scan AI.** The scan sends only safe observed metadata (`aiSignals`: the final URL, status, which security headers are present, cookie flag names, disclosed server/tech, the title — never the page body or anything the user typed) to `BudgetAiService.analyzeSurface`, which adds findings and is gated on `GEMINI_API_KEY`: with no key it returns `[]` and the scan still runs the deterministic checks (`aiUsed: false`). The reply is checked against a zod schema; AI CVSS (0.0–10.0) is stored in tenths. The scan returns `phases` (the real check groups, shown as a methodology panel in `PhaseProgressComponent`) and the stored findings. The phases are passive checks only — never active-attack phases like injection or exploit verification.
- **Space rules.** A Security space can be shared (viewers read the findings and the overview; editors add, edit and delete) but it **cannot be duplicated**. Its rows go when the space is deleted for good. There is no sidebar dot, no scheduler, no realtime push and no offline queue.
- The web (`features/security`, `/security`): a header, a four-tile risk overview (Open, Critical, High, Medium) and a table (severity badge, title + target, status, CVSS, a row menu for editors). Add and Edit share `FindingDialogComponent`. `['security', spaceId]` holds the view. Severity and status colours reuse the theme tokens (`destructive`, `signal`, `status-*`), never Tailwind palette classes.
